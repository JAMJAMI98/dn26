# 설계 (창 A, 결과는 docs/05_design.md)

1. **제약과 지표 표**: README의 반드시 조건 + 담당자 수치 답 + 데이터 하한으로 만든다. 각 행에 출처(README·담당자 #·가정).
   - 담당자 수치 답은 "반드시(제약)"와 "가능하면(지표)" 두 안을 만들어 G2에서 사용자가 고르게 한다.
   - 지표는 평균만 쓰지 않는다: 최대·p95·평균 + 상한 위반 건수.
2. **결정 표**: 지금 정해야 하는 것마다 한 줄(결정 / 근거 / 버린 대안 / 포기한 것). 후속 문답 "왜 이렇게 했나, 대안은, 포기한 것은"의 답이 된다.
   - 최적화형이면 `$dn-optimize` 1~3절로 해법 계열과 기준선을 먼저 정한다. 예측형이면 `$dn-model` 1~2절.
3. **구조와 상태 위치**: 입력 → 검증·적용 → 계산 → 검사 → 저장 → 조회·내보내기를 모듈 이름으로. 상태(활성 데이터, 결과, 세션, 작업)가 어디 있고 언제 바뀌는지 표.
4. **API 계약**: 경로·역할·입력·출력·오류. 창 C(화면)는 이것만 보고 만든다.
5. **화면 명세**(`$dn-ui` 1절): 역할별 화면 → 블록(entities 부품 이름) → 보여 줄 숫자·동작·상태 4종.
6. **서비스 점검**: 동시 요청 409 / 데이터 교체 후 이전 결과 표시·차단 / 결과 이름 안정성·초안→게시 필요 여부 / 본인 데이터만 / 빈 DB 시작.
7. **상태가 있는 업무(요청·승인·검토 흐름)**: 상태 전이표 = 현재 상태 × 행동 × 할 수 있는 역할 → 다음 상태 + 필요한 입력(사유 등). 표에 없는 전이는 409, 역할이 아니면 403. 자기 건 처리 같은 이해충돌 규칙과 금액·수량 한도 경계값은 담당자에게 확인. 이력은 덮어쓰지 않고 행을 추가(누가·언제·무엇을·왜). 테스트: 허용 전이 전부 + 금지 전이 대표.
8. **검토·판정형(변경·심사·평가)**: 판정 기준표 = 기준 / 측정 방법 / 통과 조건 / 근거 자료 / 기준 출처. 결과는 통과·조건부·불가·자료 부족 4가지, 판정마다 근거 문장과 빠진 자료 목록. 가중 점수를 쓰면 가중치 출처와 민감도. 최종 결정을 사람이 하는 단계가 필요한지 담당자에게 확인.
9. **G2 질문**(한 번에): 제약 숫자(반드시/가능하면), 우선순위, 방법 방향, 화면 블록. 각 항목 선택지 2~3개 + 추천 1개. 답을 받으면 표를 고치고 LOG D.

하지 말 것: 결정을 "추가 확인 필요"로 미루기. 확인 못 한 것은 [가정] + 설정값으로 두고 정한다.
