# 검증 (창 A 실행, 독립 재계산은 창 B. 결과는 docs/07, 근거는 docs/evidence/)

실행하지 않은 것은 PASS가 아니다. 문서에 문장이 들어갔는지는 검증이 아니다.

## 층별 확인 (해당하는 것만)
1. **규칙 검사**: 반드시 조건(C)마다 일부러 깨뜨린 입력 1개로 잡히는지. 정상 입력 위반 0.
2. **품질 하한**: 지표 상한(예: 최대 소요, 오류율) 위반 건수. 평균만 보고 PASS하지 않는다.
3. **독립 재계산**: 창 B가 원본과 요구만 보고(메인 코드·결과를 보지 않고) 핵심 숫자 2~3개를 다시 계산해 대조. 차이는 메인 오류 / 검증 오류 / 해석 차이로 분류.
4. **회귀**: 버그 수정 전 실패를 먼저 보고(로그 보존) → 수정 → 같은 입력 PASS.
5. **서비스**: 권한(다른 역할 403·남의 데이터 거절), 잘못된 데이터 적용(파일·행·이유, 기존 유지), 데이터 교체 직후 이전 결과 표시·차단, 동시 요청 409, 재시작 후 유지.
6. **배포**: `docker build` → 실행 → 준비될 때까지 기다린 뒤 /health 200. docker가 없으면 NOT_RUN과 이유.
7. **요구 대응**: docs/02의 R·C마다 상태와 근거. Must가 하나라도 NOT_RUN이면 보고에 먼저 쓴다.
8. **화면**: 사용자가 G3·G5에서 직접 확인 → HUMAN_CHECK, 확인 순서 3~5단계를 적어 준다.

## 기록
- `python3 /tmp/dn/tools/ev.py "명령" --claim "주장"` → docs/LOG.md에 V, 로그는 docs/evidence/. 증거로 쓸 실행은 커밋 후. 동시에 두 번 돌리지 않는다.
- 테스트는 pytest 표준 출력(passed/failed 집계). 자체 스크립트 검사도 pytest에서 호출되게 하면 좋다.
- "~일 것이다, 거의 됐다"가 나오면 확인 명령부터 돌린다.
- 기능 동결 후 한 번: `/review` 또는 Review Agent, 보안 스킬이 있으면 1회.
