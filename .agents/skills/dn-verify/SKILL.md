# 검증

실행하지 않은 확인은 PASS로 적지 않는다. 순서: 무엇이 증명하나 → 새로 실행 → 출력과 종료 코드 읽기 → 주장과 대조 → 그다음 말하기.

## 1. 확인 목록
`PLAN.md`의 요구 번호(R1…)와 "이 과제 고유 규칙"을 하나씩 나열하고 (Must 요구는 하나도 빠지면 안 된다. 요구 번호 ↔ V 번호 표를 HANDOFF에 남긴다), 각각 가장 싼 확인 방법을 정한다.
- 계산·규칙: 작은 테스트. **값 하나는 손계산이나 다른 방법으로 구한 값과 비교**한다.
  - 기대값은 담당자 답·README·손계산에서 온다. 테스트가 실패하면 기대값이 아니라 코드를 고친다. 기대값을 바꿔야 하면 사용자에게 묻고 LOG.md D 항목. 기대값 출처(Q번호·README 줄)를 테스트 이름이나 주석에 붙인다.
  - 회귀 테스트는 실패를 직접 본다: 수정 되돌림 → 실패 확인 → 복원 → 통과. 실패를 본 적 없는 테스트는 증거가 아니다. 오타·import 오류로 난 실패는 실패로 치지 않는다.
- 데이터 처리: 행 수 보존, 매칭 실패 0, 제외 건수, 중복 제거 전후 수치
- API·서버: `curl`로 정상 입력, 빈 입력, 잘못된 입력 각 1회
- LLM 기능: 정상 1개, 이상한 입력 1개, 실패 시 대체 동작
- 화면: 사용자가 미리보기에서 누를 순서 3~5단계 → `HUMAN_CHECK`

## 2. 실행과 기록
- 주장마다 필요한 증거가 다르다. 오른쪽 열로는 PASS를 적지 않는다.

  | 주장 | 필요한 증거 | 증거가 아닌 것 |
  |---|---|---|
  | 테스트 통과 | 이번에 새로 돌린 출력, 실패 0 | 이전 실행, "통과할 것" |
  | 버그 고침 | 원래 증상 재현 입력으로 재실행 | 코드를 바꿨다는 사실 |
  | 서브에이전트 완료 | `git diff`로 실제 변경 확인 | 에이전트의 "성공" 보고 |
  | 요구 충족 | R번호별 확인 | 테스트 전부 통과 |
- "~일 것이다, 아마, 보인다, 거의 됐다"가 나오면 그 문장은 실행 전이다. 확인 명령부터 돌린다. 출력에 경고·오류 로그가 섞여 있으면 통과로 적지 않고 원인을 한 줄 남긴다.
- 기본 방법: `python3 /tmp/dn/tools/ev.py "명령" --claim "주장" --src "파일:줄"` → 로그 저장과 LOG.md V 항목이 자동으로 남는다.
- 증거로 쓸 실행은 커밋한 뒤 돌린다. 실패하면 고치기 전에 원인을 한 줄로 적는다.
- `LOG.md`에 남긴다:
```
## V3. 매칭 실패 0건 (규칙 2)
- 방법: python scripts/check_join.py
- 결과: PASS (unmatched=0, rows 1200→1200)
- 근거: outputs/join_check.txt, src/normalize.py:14
```

## 2-1. 흔한 실패 점검 (해당하는 것만)
- ID·문자열을 부분 일치로 매칭하지 않았나 (정확 일치·정규화)
- 외부 호출(LLM, 파일, 네트워크) 하나가 실패해도 서버·파이프라인이 계속 도는가
- 빈 입력, 0, 음수, 경계값(같은 값이면 통과인가), 중복 입력
- 결측을 0으로 채우지 않았나, 분모에서 뺄 대상을 뺐나
- 같은 입력을 두 번 넣으면 같은 결과인가 (정렬 기준, tie-break, seed)
- 코드 속 상수·임계값마다 출처가 있나 (없으면 HUMAN_CHECK로 남기고 담당자 질문 목록에)

## 2-2. 분석 결과 검증 방법 (원인·집계 과제)
- **3자 대조**: 원천 데이터 ↔ 중간 결과(쿼리·표) ↔ 최종 답(화면·LLM 응답). 숫자 하나를 세 곳에서 같은지 본다
- **매칭률**: 조인·귀속 경로마다 매칭률을 숫자로 남긴다 (`joincheck.py`)
- **대조군**: 이상 기간 vs 평상 기간, 후보 설비 vs 다른 설비
- **반증**: 결론이 틀렸다면 보여야 할 데이터를 찾아본다. 없으면 그 사실도 기록
- **경계 사례**: 빈 입력, 대상 없음, 모호한 질문, 범위 밖 질문을 각각 1개씩 실행
- **수치 크기**: 행 수·중복 수를 각 단계 전후로 기록해 행 팽창·누락을 잡는다
- **적재·변환 4단 점검**(데이터를 다른 구조로 옮겼다면): 수량(원천 vs 결과 건수) → 값(속성 값·타입 일치) → 구조(관계가 빠짐없이 연결) → 논리(원천에서 조인한 답 = 새 구조에서 조회한 답)
- **검증 안 된 예시 수치는 결과물에 넣지 않는다** ("신뢰도 85%" 같은 그럴듯한 숫자 금지). 샘플·합성 데이터 결과면 그 전제를 화면과 README에 적는다

## 2-3. 실패 추적 (고치기 전에)
- 원인을 찾기 전에는 고치지 않는다. 오류 메시지를 끝까지 읽고 재현 명령부터 고정한다. 재현이 안 되면 고치지 않는다.
- 여러 단계(입력 → 처리 → API → 화면)면 경계마다 들어온 값·나간 값을 출력해 **어느 경계에서 깨지는지**부터 찾는다.
- 정상 동작하는 사례와 비교해 차이를 전부 적는다.
- 가설은 하나만: "원인은 X, 근거는 Y". 한 번에 하나만 바꾼다. 틀리면 수정을 쌓지 말고 되돌린 뒤 새 가설. 시도한 가설은 LOG.md에.
- 원인이 외부·타이밍이면 조사한 것을 LOG.md에 적고 재시도·타임아웃·오류 메시지로 처리한다.
- 멈춤 신호: "일단 이것만 바꿔 보고", "여러 개 같이 고치고 돌려 보자", "고치는 김에". 바뀐 줄은 전부 이 수정으로 설명돼야 한다.

## 3. 사전 부검 (5분)
"이 결과가 틀렸다면 가장 그럴듯한 이유 2가지"를 쓰고, 각각 확인하거나 한계로 남긴다.

## 4. 독립 재계산 (핵심 숫자가 있는 과제면 권장)
- 작업 폴더에 `.codex/agents/verifier.toml`이 있고 신뢰한 폴더면, **verifier 서브에이전트**에게 검증 항목(최대 5개)만 넘긴다. 메인 코드·결과·LOG.md는 넘기지 않는다.
- verifier가 `verify/`에 독립 계산을 끝내면 메인 결과표를 넘겨 대조시킨다. 불일치는 (a) 메인 오류 (b) 검증 오류 (c) 해석 차이로 나누고, (c)는 담당자 질문으로 넘긴다.
- 요청문에 "이건 문제 삼지 마"를 쓰지 않는다. 오탐은 결과를 받은 뒤 판정한다.
- 서브에이전트가 막혔다고 하면 같은 지시로 재시도하지 않는다 (맥락 추가 / 작업 쪼개기 / 계획 수정 중 하나).
- toml이 설치되지 않았어도(작업 폴더가 홈) 서브에이전트는 말로 띄울 수 있다: "verifier 서브에이전트를 띄워서 `/tmp/dn/.codex/agents/verifier.toml`의 developer_instructions를 지침으로 주고 …". 그래도 안 되면 새 터미널에서 `codex`를 켜고 `/tmp/dn/.codex/agents/verifier.toml 의 developer_instructions 대로 독립 검증자 역할을 해. 검증 항목: …`으로 같은 일을 시킨다.

## 4-1. 도메인 리뷰 (규칙·계산이 많은 과제면 권장, 반복 단계 중간에 1회)
- **reviewer 서브에이전트**(없으면 새 터미널 Codex에 `/tmp/dn/.codex/agents/reviewer.toml 지침대로 리뷰해`)(읽기 전용)에게 "PLAN.md 기준으로 src/ 의 도메인 오류를 찾아줘"만 넘긴다. 테스트는 통과하지만 업무적으로 틀린 코드, 출처 없는 기준값을 찾는다.
- 판단 불가 항목은 담당자 질문으로 돌린다. 반영 여부는 LOG.md D 항목.

## 5. 별도 세션 리뷰 (선택, 시간 여유 있을 때)
가장 싼 방법: 같은 세션에서 `/review` 또는 Codex 기본 스킬 **Review Agent**(코드 변경에서 실제 버그 찾기)를 1회 돌리고, 지적을 아래 규칙대로 처리한다. 시간이 더 있으면 새 세션으로:
새 터미널에서 새 Codex 세션을 열고 이 문장을 준다 (수행 대화를 이어받지 않은 눈으로 본다):
```
PLAN.md, LOG.md, git log --oneline, git diff HEAD~5 를 읽고 성공 기준 대비 빠진 것, 검증되지 않은 주장, 숫자 불일치를 찾아 표로 알려줘. 코드는 고치지 마.
```
지적마다 자기 말로 다시 쓰고 → 코드·출력으로 사실 확인 → 반영하거나 근거 있게 반박한다. 하나라도 불명확하면 아무것도 반영하지 말고 그것부터 묻는다. 반영 여부는 `LOG.md`에 `D` 항목.

## 4-2. 보안 점검 (검증 단계에서 1회)
- `/skills`에 security-best-practices가 있으면: `$security-best-practices 이번 과제 코드 전체(키·개인정보 처리, 입력 검증, 외부 호출, 오류 노출)를 점검해. 고칠 것만 표로(파일:줄 / 위험 / 고칠 방법), 코드는 아직 고치지 마.`
- 지적은 4절 규칙대로 사실 확인 후 반영. 반영한 것·안 한 것과 이유를 LOG.md D 항목, 결과 요약을 HANDOFF "결과를 믿을 수 있는 이유"에 한 줄
- 스킬이 없으면 같은 항목을 직접 확인: `grep -rniE "api_key|secret|token|password" --include=*.py --include=*.js .`, `.env`가 `.gitignore`에 있는지, LLM에 보내기 전 가리기, 오류 메시지에 내부 경로·키 노출 여부

## 5-1. 담당자에게 결과 확인
- 핵심 기능이 돌면 담당자에게 보낼 **결과 요약 5줄**(숫자 포함, 기술 용어 없이)을 써서 사용자에게 준다. 사용자가 메신저로 보내고, 반응을 PLAN.md Q&A와 LOG.md D 항목에 남긴다.

## 6. 마지막에 따로 적는다
- 아직 확인 못 한 것 (`NOT_RUN`, `HUMAN_CHECK`)
- 알려진 약점: 어디서, 어떤 입력에서 틀릴 수 있나 → 그때 무슨 일이 생기나
