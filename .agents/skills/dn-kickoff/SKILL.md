# 시작과 합의

## 0. 빠른 경로 판단
README에 목표, 데이터, 제출물, 평가 기준이 이미 구체적이면 이 단계는 10분 안에 끝낸다. 요약 → 미확인 1~3개 질문 → BRIEF.
먼저 말한다: "이건 [확인용 실험 / 기존 흐름 수정 / 새 구조]로 보고 [채팅에 짧게 / PLAN.md에] 설계합니다." 헷갈리면 무거운 쪽. 도중에 숨은 복잡도가 보이면 멈추고 올린다.

## 1. 읽기 (구현 금지)
- README, 디렉터리 구조, 데이터 파일 이름·크기·형식, 제출물 형식과 경로, 과제가 지정한 문서 이름
- 환경: `git --version; python3 -V; node -v; date '+%F %T %Z'` / 데이터 과제면 `python3 -c "import pandas"`
- 서버 시간대가 KST가 아니면 종료·제출 시각을 서버 시각으로도 적는다.
- 사용자에게 보고: 요청 한 문장 / 과제 유형(분석 · 구현 · 예측) / 제출물(README 문구 그대로) / README만으로 정해지지 않는 것 최대 5개

## 2. 담당자 질문과 답 기록
`$dn-interview`를 쓴다. 질문을 만들고, 답이 올 때마다 기록한다. 담당자 답이 오기 전까지는 BRIEF 초안을 [가정]으로 채워 둔다.

## 3. BRIEF (PLAN.md 맨 위)
```
# PLAN
## BRIEF
- 업무 질문: (누가 무엇을 결정하려고 이걸 쓰나) [사용자]
- 다시 정한 문제: (한 문장)
- 요구 목록: `R1`, `R2` … 번호를 붙인다 (README 필수 요구 + 담당자 답). 각각 Must / Should 표시. 검증(V)과 커밋 메시지에서 이 번호를 쓴다
- 성공 기준: (요구 번호별 확인 방법 / 출처: 담당자 Q? | README | [가정]) [사용자]
- 한다 / 안 한다(이유) [사용자]
- 범위 조건: (기간, 대상, 포함·제외 레코드 조건) 표로 고정. 이후 모든 숫자의 전제
- 평가 기준이 공개돼 있으면: 기준 항목 ↔ 설계 결정 대응표 (README·HANDOFF에서 그대로 쓴다)
- 제출물: (형식, 경로)
- 기술 선택: (고른 것 / 버린 대안 / 이유)
- 시각표(KST): 첫 완주 / 70% / wrap / 읽기 / 제출 / 종료
- 가정: (답 없이 정한 것)
- 데이터가 늦거나 명세만 있으면: 명세로 작은 합성 샘플을 만들어 파이프라인부터 끝까지 돌리고, 실데이터가 오면 교체
## 작업 목록
1. (성공 기준 하나 = 작업 하나. 확인 방법 포함)
```
- `[사용자]` 줄은 사용자가 자기 말로 정한다. AI는 후보만 낸다.
- 결정 근거로 쓴 담당자 답은 짧게 인용한다.
- 작업 목록 금지어: "적절한 예외 처리", "엣지 케이스 처리", "나중에", "TBD", "위와 비슷하게". 대신 어떤 입력에서 무엇이 나와야 하는지 쓴다.
- 작업 목록을 다 쓰면 R번호마다 담당 작업 번호를 짚는다. 짚을 수 없는 R은 작업을 추가한다.
- 정해진 값(포트, 파일명, 형식, 기준값)은 README·담당자 답의 문구를 그대로 복사한다.
- 합의 후 요약 3줄(다시 정한 문제, 성공 기준, 안 하는 것)을 사용자가 담당자에게 보내 확인받는다. 기다리는 동안은 읽기 전용 데이터 점검만 한다.
- 그다음 `.gitignore`(`.env`, 키, 큰 중간 파일, 로그)를 만들고 `git status --short` 확인 후 만든 파일만 이름으로 add해 커밋: `plan: 문제 정의 합의`. (작업 폴더가 홈이면 기존 untracked 파일이 많다. 과제 원본·플랫폼 파일은 건드리지 않는다)
