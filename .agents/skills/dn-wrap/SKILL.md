# 마무리

## A. 세션 교체 (대화가 길어지거나 느려질 때 언제든)
`HANDOFF.md` 맨 위 "현재 상태"만 갱신하고 사용자에게 새 세션을 권한다.
```
## 현재 상태 (시각)
- 남은 시간 / 지금 단계(PLAN 작업 번호):
- 방금 한 것 / 막힌 것:
- 다음 한 가지:
- 꼭 읽을 파일:
```
새 세션 첫 입력: `AGENTS.md와 HANDOFF.md 읽고 현재 상태부터 이어서 해줘.`

## B. 제출용 HANDOFF.md
`PLAN.md`, `LOG.md`, `git log --oneline` 근거로만 쓴다. 근거 없는 내용은 쓰지 않는다.
```
# HANDOFF
## 차이 (기대·요구와 다른 결과. 없으면 "없음")
## 무엇을 만들었나 (담당자 말로 3줄)
## 실행 방법 (명령 한 줄, 포트, 사용 순서)
## 성공 기준별 상태 (PASS/FAIL/NOT_RUN/HUMAN_CHECK, 근거 V번호)
## 결과를 믿을 수 있는 이유 (검증 질문 2~3개 → 각각 증거 V번호·화면)
## 일부러 안 한 것과 이유
## 알려진 약점과 위험
## 다음에 할 일 (우선순위)
## 담당자에게 남은 질문
```

## C. 제출 점검 (종료 15분 전까지)
남은 시간에 무엇을 버릴지는 선택지 2~3개로 내고 사용자가 고른다. 최종 실행이 실패하면 정리를 시작하지 말고 실패 목록부터 보고한다.
1. README가 요구한 제출물, 경로, 파일명과 실제를 대조한다.
2. 최종 실행을 **새로** 한 번 돌린다 (기존 로그 재사용 X).
3. `git status`가 깨끗한지, 모든 편집기 탭이 저장됐는지, 외부 변경 충돌이 없는지.
4. 키, 토큰, `.env`가 커밋에 없는지: `git log -p | grep -iE "api_key|token|secret"` 결과 없음.
5. README에 **"어떻게 동작하나"** 단락이 있는지: 구성 요소 3~5개 / 데이터 흐름 / 왜 이 구조인가 / 어디서 깨질 수 있나. 사용자가 이걸 읽고 후속 문답에서 코드 구조로 설명할 수 있어야 한다.
6. 마지막 커밋: `wrap: 인계와 최종 검증`.

## D. 후속 문답 대비 (사용자가 직접 읽는다)
`LOG.md`, `PLAN.md`, 핵심 코드 기준으로 아래 질문 은행에서 이 결과물에 해당하는 6개를 고른다.
- 의도: 사용자는 누구고 어떤 결정을 돕나 / 반드시 지킬 조건과 조정할 조건을 어떻게 나눴나 / 명시되지 않은 것 중 무엇을 가정했나 / 하지 않기로 한 것과 이유 / AI에게 맡긴 것과 직접 한 것의 경계 / AI 출력을 어디서 믿지 않았나 / 작업을 어떻게 쪼갰나 / 중간에 방향을 바꾼 계기
- 기술: 어디서 어떻게 실행되나(명령 한 줄) / 같은 입력에 같은 출력 보장 / 실패하면 사용자가 아나 / 비밀·개인정보 처리 / 데이터 10배면 어디가 먼저 무너지나 / 더 단순한 대안은 왜 부족했나 / 실패하는 테스트를 직접 봤나
- 인지: 가장 약한 곳 / 틀린 답을 내는 입력 하나 / 설명 못 하는 코드 줄 / 다시 한다면 / 시간이 2배면 / 지표와 실제 업무 목표의 연결 / 내일 실무에 넣으면 먼저 확인할 것
답하다 막히는 질문은 문서에 없는 것이다. 지금 HANDOFF에 한 줄 적는다. 끝까지 모르면 "그건 확인하지 않았습니다"로 정직하게 연다.
- 왜 이 방식을 골랐나 (파일·함수를 짚어서) / 담당자의 어떤 말이 이 기능을 만들었나
- 무엇을 가정했고, 그 가정이 틀리면 무엇이 깨지나 / 일부러 안 만든 것과 이유
- AI에게 무엇을 맡기고 무엇을 직접 했나, AI 출력을 어디서 믿지 않았나 (LOG의 E 항목)
- 이 입력이 들어오면 어떻게 되나 (빈 값, 예외, 데이터 10배) / 같은 입력에 같은 결과를 어떻게 보장하나
- 결과가 맞다는 걸 어떻게 확인했나, 테스트가 실패하는 걸 직접 봤나 / 가장 약한 곳과 다음 개선
설명 소재: 임계값·프롬프트·기간 같은 조정값은 코드 밖 설정 파일로 빼 둔다 → "코드 수정 없이 담당자가 바꿀 수 있다"(확장성·운영 질문). 실패 사례를 설계 이유로 연결한다 (예: "인자 빠진 질문은 되묻게 했다 → 전부 넘기면 근거 없는 답이 나와서"). 단계 구분: 지금 된 것 / 다음 단계 / 그 이후.
답 틀: **무엇을 했다 → 왜(근거) → 약점·위험 → 다음 확인이나 개선**. 질문의 전제가 실제 구현과 다르면 첫 줄에서 바로잡는다.
`HANDOFF.md` 끝에 "읽을 것" 절을 둔다 (사용자가 5분 안에 읽을 분량):
- 핵심 5줄: 핵심 결정 3개, 최대 약점 1개, 다음 단계 1개
- 숫자 3개: 결과를 대표하는 숫자와 출처(파일·V번호)
- 구조 한 줄: 입력 → 처리(파일·함수) → 출력
- 예상 질문 6개와 각 답의 **키워드 한 줄**(문장으로 쓰지 않는다. 근거 파일·함수·LOG 번호를 포함)
